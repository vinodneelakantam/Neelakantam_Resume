# Embedded Build Systems Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | Explain cross-compilation and the problems it introduces. | Cross-compilation builds on a host for a different target architecture. It requires a matching compiler, sysroot, ABI, libraries, CPU options, linker scripts, and target assumptions. Common failures are host contamination, incompatible library versions, wrong floating-point ABI, and missing runtime dependencies. A pinned toolchain and isolated build environment make these failures diagnosable. |
| 2 | How would you structure a maintainable CMake project for an ECU? | I would use target-based CMake with explicit include paths, compile definitions, link dependencies, and interface properties. Toolchain files describe the cross environment, while presets capture supported configurations. Components expose narrow targets instead of global flags. Generated files remain in the build tree, and CI tests clean builds to detect accidental local dependencies. |
| 3 | What is Yocto, and how do recipes, layers, and images relate? | Yocto uses BitBake metadata to build a tailored Linux distribution. A recipe defines how to fetch, configure, compile, package, and license a component. Layers organize related recipes and configuration with controlled priorities. An image selects the packages and features delivered to the target. Machine and distribution configuration separate hardware policy from product policy. |
| 4 | How do you make Yocto builds reproducible? | I pin layer revisions, source checksums, mirrors, configuration, host/container environment, and the generated dependency manifest. Shared-state and download caches improve speed but should not hide undeclared inputs, so clean verification builds are important. Release records include image metadata, package versions, licenses, tool versions, and build configuration alongside the binaries. |
| 5 | How does a Zephyr build differ from a Linux distribution build? | Zephyr produces a compact RTOS firmware image configured through boards, devicetree, Kconfig, and CMake-based west tooling. It generally links application and selected subsystems together rather than assembling a package-based root filesystem. Integration therefore focuses heavily on compile-time configuration, memory constraints, device bindings, real-time behavior, and board-specific overlays. |
| 6 | What should you consider when integrating an AOSP-based platform? | AOSP integration spans manifests, repositories, Soong or Make build definitions, vendor components, kernel and device configuration, SELinux policy, interfaces, and signed partitions. I control source revisions and proprietary dependencies, preserve compatibility boundaries, run platform tests, track image sizes, and ensure that signing and update metadata match the target's verified boot strategy. |
| 7 | How do you diagnose a linker error in a large C/C++ build? | I classify it as an undefined symbol, duplicate symbol, incompatible object, section overflow, or ordering problem. Then I inspect the exact link command, symbol tables, library order, ABI flags, map file, and conditional compilation. A minimal reproducer or dependency trace often reveals whether the defect belongs to configuration, an interface change, or the build graph. |
| 8 | When are incremental builds unsafe? | They are unsafe when dependency declarations are incomplete, generated files are stale, configuration changes are not represented in the graph, or tools write undeclared outputs. I compare incremental output with periodic clean builds and artifact hashes. Any discrepancy is treated as a build-system defect because developers and CI must obtain equivalent results from the same declared inputs. |
| 9 | How do you optimize a large embedded build without sacrificing correctness? | I profile first, then address expensive compilation units, serialization, repeated code generation, dependency downloads, and unnecessary variant rebuilds. Safe techniques include compiler caching, shared immutable caches, parallel execution, prebuilt approved toolchains, and better dependency boundaries. Clean-build checks and cache-key validation ensure optimization does not reuse incompatible outputs. |
| 10 | What information belongs in a build manifest? | A useful manifest includes source commits, submodules or layer revisions, dependency versions and checksums, toolchain and container identity, configuration and variant, build flags, generated artifact hashes, and pipeline provenance. For release use, I also link SBOM, test evidence, signatures, and approvals, enabling reproduction and field-issue traceability. |
