# Embedded Platform Integration Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | What are the main phases of integrating software on a new ECU platform? | I start with hardware and software interface assumptions, toolchain and boot-chain readiness, then integrate low-level drivers, operating system, middleware, and application components incrementally. Each increment gets build, flash, smoke, communication, and resource checks. Configuration and dependency baselines are controlled so failures can be traced to a specific integration step. |
| 2 | How do you approach board bring-up when the target does not boot? | I verify power, reset, clocks, boot straps, memory initialization, and the earliest observable boot stage in that order. UART traces, debugger halt locations, register values, and known-good images narrow the fault. I change one variable at a time and record results, separating hardware issues from bootloader, device-tree, linker, or driver configuration problems. |
| 3 | How do you manage dependencies across a large ADAS platform? | I use a versioned manifest or equivalent dependency model with compatible baselines, ownership, and approved update rules. CI checks availability, version constraints, interfaces, licenses, and known vulnerabilities before building. Candidate baselines are tested as a unit, and released artifacts retain the complete dependency graph so a field issue can be reproduced later. |
| 4 | What makes multi-variant ECU integration difficult? | Variants may differ in hardware, calibration, feature flags, memory maps, peripherals, and customer configuration. Uncontrolled conditional compilation creates combinations that are hard to test. I prefer explicit configuration schemas, validated overlays, generated manifests, and a risk-based build/test matrix, while maximizing common code and clearly identifying every variant artifact. |
| 5 | How would you isolate an integration failure after merging several components? | I first compare against the last known-good baseline and classify the failure by boot phase, interface, timing, or functional behavior. Binary search across changes, component rollback, logs, traces, and interface contract checks identify the smallest failing combination. The final fix should include a regression test at the lowest layer that reliably detects the defect. |
| 6 | How do you coordinate cross-functional integration for an ADAS release? | I establish a shared baseline, interface and dependency owners, entry criteria, integration sequence, milestone dates, and escalation paths. A daily view of build status, blockers, test evidence, and open deviations keeps architects, developers, testers, project managers, and release teams aligned. Decisions and accepted risks are documented against the release candidate. |
| 7 | What is the role of configuration management in platform integration? | Configuration management defines exactly which source, tools, dependencies, calibration, build options, and hardware revisions form a product baseline. Without it, a successful build cannot be reproduced or compared. I enforce reviewed changes, immutable release tags, generated manifests, access control, and traceability from requirements and defects to the delivered binary. |
| 8 | How do you validate resource usage during integration? | I compare flash, RAM, stack, CPU load, startup time, and communication bandwidth against allocated budgets. Linker maps and static reports give early evidence, while target measurements cover dynamic peaks and timing. CI should detect budget regressions, but threshold changes require owner review because a passing total can still hide local exhaustion. |
| 9 | How do SIL and HIL complement platform integration? | SIL gives fast, scalable feedback for algorithms, interfaces, and regression scenarios without scarce hardware. HIL validates real timing, buses, I/O, fault injection, and interaction with the target ECU. I use SIL early and often, then select HIL tests for hardware-dependent and safety-relevant behavior; results from both are tied to the same baseline. |
| 10 | How do you know an integrated platform is ready for release? | Readiness requires more than a green build. The baseline must be reproducible, required tests and quality gates must pass, interfaces and variants must be covered, defects and deviations must be assessed, cybersecurity evidence must be complete, and artifacts must be signed and traceable. Authorized stakeholders then approve the identified candidate for promotion. |
