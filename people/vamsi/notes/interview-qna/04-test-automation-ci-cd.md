# Test Automation & CI/CD Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | How do you integrate HIL test execution into a Jenkins CI/CD pipeline? | I wrap the LabVIEW TestStand/Python test sequences behind a command-line entry point that Jenkins can trigger per build, capture structured results (pass/fail, logs, traces) as build artifacts, and gate promotion of a build on the pipeline's test stage passing. Rig availability is scheduled so parallel builds don't collide on shared hardware. |
| 2 | How do you structure Python-based regression and fault-injection scripts so they stay maintainable? | I separate rig-control code (FIU, power, signal generation) from test-case logic and expected-result definitions, so a new fault scenario is a data/config change, not a new script. Common assertions and logging utilities are shared across scripts to keep result formats consistent for later CI ingestion and reporting. |
| 3 | How do you manage test case traceability with Jira or a tool like Continental's ATP/TEMPPO? | Every test case links back to a requirement ID, and every execution result links back to the test case and the build/baseline it ran against. This traceability chain is what lets me answer "which requirements are verified in this release" during an ASPICE audit or release review without manually reconstructing history. |
| 4 | How do you handle flaky tests in an automated HIL pipeline? | I first confirm whether the flakiness is rig-related (timing, connector wear, power stability) or a genuine intermittent defect by rerunning on a second rig or with tighter timing margins. Tests that can't be made deterministic are quarantined from the release gate but still tracked, rather than silently ignored, so real defects aren't hidden by "known flaky" status. |
| 5 | How do you use Git/Gerrit/GitLab in an embedded test workflow? | Test scripts, TestStand sequences, and configuration files go through the same review process as production code, using Gerrit/GitLab merge requests. This catches accidental changes to fault thresholds or expected values before they silently weaken a release gate. |
| 6 | How do you report and track defects found during automated test runs? | Each failure is filed with the exact test case, build/baseline, bus trace or log excerpt, and reproduction steps, then triaged with the development team using severity and requirement linkage from Jira. I follow up to confirm the fix is verified against the same automated case that originally caught it, closing the loop. |
| 7 | How do you scale test automation across multiple ECU variants or programs? | I parameterize test cases by variant (ECU configuration, ARXML baseline, calibration set) rather than duplicating scripts, and maintain a variant-to-configuration mapping so the same automated suite can run against any supported variant with minimal setup change. |
| 8 | What metrics do you track to judge whether test automation is actually effective? | Requirement coverage, defect escape rate (issues found later that automation should have caught), flaky-test ratio, and rig utilization/turnaround time are the ones I watch most, since a high pass rate alone doesn't tell you whether the suite is actually catching real problems. |
