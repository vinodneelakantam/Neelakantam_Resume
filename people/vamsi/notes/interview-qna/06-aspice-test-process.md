# ASPICE-Aligned Test Process Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | What do HWE.2, HWE.3, and SWE.5 cover, and how do they relate to your test work? | HWE.2/HWE.3 cover hardware design verification and integration, while SWE.5 covers software integration and testing against requirements. As a HIL/SIL test engineer I sit mostly in HWE.3/SWE.5, verifying that integrated hardware/software meets its documented requirements with objective, traceable evidence. |
| 2 | How do you ensure test process compliance on an ASPICE-audited program? | I make sure every test case traces to a requirement, every execution result is stored with the build/baseline it ran against, and any process deviation is documented rather than silently worked around. Audit readiness is a byproduct of doing this consistently during the program, not a activity done just before the assessment. |
| 3 | How do you maintain traceability between requirements, test cases, and defects using a tool like IBM DOORS? | I link each test case to its source requirement in DOORS and each defect back to the failing test case, so a requirement's verification status can be queried directly instead of reconstructed from spreadsheets. This traceability is what an assessor checks first. |
| 4 | How do you use PTC Integrity or MKS for configuration management on a test program? | I baseline test scripts, ARXML configuration, and expected-result data together, so a given release can always be reproduced exactly, including which test suite version verified it. Uncontrolled changes to expected values are the most common way test evidence quietly becomes invalid. |
| 5 | How do you handle process assessments or audits as a test engineer? | I prepare by walking my own traceability chain end-to-end beforehand: pick a sample requirement, show its test case, its latest execution result, and any linked defects. If I can't answer that chain quickly, it means my process discipline needs fixing before the assessor asks. |
| 6 | What test documentation artifacts do you typically produce for ASPICE evidence? | Test plans, test case specifications with requirement links, execution reports with pass/fail and environment details, and defect reports with severity and resolution status are the core set. I keep these versioned alongside the software baseline they verify. |
| 7 | How do you balance Agile/Scrum sprint cadence with ASPICE process discipline? | Each sprint's test scope is still tied to specific requirements and produces the same traceable artifacts, just delivered incrementally rather than in one large phase. The discipline doesn't disappear in Agile, it just needs to fit inside a shorter cycle. |
| 8 | How do you manage a change request that affects an already-validated test baseline? | I identify every test case tied to the affected requirement, re-run and re-baseline those specifically rather than assuming the rest of the suite is unaffected, and record the change's impact on the traceability chain so the audit trail stays accurate. |
