# AUTOSAR & Gateway/Telematics/Body ECU Integration Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | What is AUTOSAR and how does it structure ECU software? | AUTOSAR is a layered software architecture standard that separates application (SWCs), runtime environment (RTE), and basic software (BSW) so application logic is portable across ECU hardware. I work mainly at the configuration and integration level: wiring SWC ports, RTE connections, and BSW modules (communication, diagnostics, memory) through tools rather than hand-writing the middleware. |
| 2 | How do you use DaVinci or EB Tresos during ECU integration? | I use these tools to configure communication stacks, diagnostic services, and module parameters, generate the resulting BSW/RTE code, and verify the generated configuration against the ECU's network and diagnostic specification before build. Any mismatch between the ARXML source and the generated code is caught here, before it reaches the rig. |
| 3 | What is an ARXML file and how do you manage it during integration? | ARXML is the XML-based AUTOSAR exchange format describing software components, communication matrices, and ECU configuration. I treat ARXML files as version-controlled artifacts with the same change-review discipline as source code, since an unreviewed ARXML edit can silently change signal routing or diagnostic behavior across the whole vehicle network. |
| 4 | How do you approach integrating a Gateway Control Unit, such as the ICAS1 on the VW ID.3 platform, into a vehicle program? | I start from the gateway's routing and diagnostic requirements, verify the communication matrix against the vehicle network architecture, then validate routing, timing, and diagnostic behavior sprint by sprint on the HIL rig alongside in-vehicle checks. Each sprint release gets a defined test scope so gaps are caught before they compound in later builds. |
| 5 | How do you validate gateway routing and signal behavior between vehicle network domains? | I use CANoe/CANalyzer to trace signals on both sides of the gateway and confirm that routed messages preserve timing, content, and priority as specified. I specifically test boundary cases: bus-off recovery, network management state transitions, and routing under partial network failure, since these are common sources of subtle gateway defects. |
| 6 | How do you coordinate AUTOSAR module integration across cross-site development teams in an Agile setup? | I keep a shared Jira backlog with clear interface ownership per module, agree on ARXML baseline versions at sprint boundaries, and flag any interface change immediately to the owning site rather than waiting for integration testing to surface it. This keeps sprint-level integration predictable even when component owners are in different locations. |
| 7 | What integration issues are most common at the AUTOSAR BSW/RTE boundary? | Mismatched signal data types or timing assumptions between SWCs, incorrect RTE port connections after a configuration regeneration, and diagnostic session/service conflicts introduced by an unreviewed ARXML change are the most frequent. I catch most of these by diffing generated configuration against the previous baseline before flashing. |
| 8 | How do you handle software flashing and diagnostics for AUTOSAR-based ECUs during integration? | I use tools like VW ODIS alongside ICAS1/PE Micro debuggers to flash builds, run diagnostic session checks, and confirm DTC behavior matches the release under test. Flashing failures are triaged first against known bootloader/security-access issues before treating them as application defects. |
