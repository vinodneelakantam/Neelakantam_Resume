# Secure OTA/SOTA Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | What security properties should an automotive OTA update provide? | An update needs authenticity, integrity, confidentiality where required, anti-rollback protection, authorization, freshness, and traceability. It must also preserve availability and functional safety through power loss, network interruption, storage limits, and incompatible dependencies. Security covers the backend, distribution path, vehicle gateway, target ECU, keys, package format, and operational process. |
| 2 | How does package signing protect an update? | A trusted private key signs a canonical package digest or signed metadata. The ECU verifies the signature using an authenticated public key before installation, proving origin and detecting modification. Signing does not encrypt content or prove the software is defect-free. Key protection, algorithm policy, certificate lifecycle, metadata coverage, and secure verification code remain critical. |
| 3 | What is the difference between signing and hashing? | A cryptographic hash provides a compact integrity value but, by itself, anyone can replace both content and hash. A digital signature binds the digest to a private key, providing authenticity and integrity when the public key is trusted. OTA systems commonly hash individual payloads and sign metadata that identifies versions, dependencies, hashes, sizes, and targets. |
| 4 | How would you design a robust partial-update strategy? | I define independently updateable components with explicit versions, compatibility constraints, dependencies, storage boundaries, and rollback behavior. Signed metadata identifies every payload and the valid target configuration. The vehicle verifies prerequisites before installation and validates the complete post-update state. Testing covers mixed versions, interrupted transfers, low storage, and recovery from each transition point. |
| 5 | How do A/B partitions improve update reliability? | The update is written to an inactive slot while the active system remains bootable. After verification, the bootloader attempts the new slot and commits it only after health criteria pass. A boot counter or watchdog returns to the previous slot after failure. Costs include extra storage and careful handling of shared mutable data and schema compatibility. |
| 6 | How do you prevent rollback to a vulnerable firmware version? | Signed metadata includes a monotonic security version or rollback index checked against protected ECU state. The updater rejects validly signed packages below the permitted level. Emergency recovery must follow a controlled authorization path rather than disabling the check. Version policy should distinguish ordinary product versioning from security-relevant minimum versions. |
| 7 | What should happen if power is lost during installation? | The process must be transactional: write to an inactive area, verify before activation, and update boot metadata atomically. The bootloader recognizes incomplete state and selects a known-good image or recovery mode. Design and HIL testing should inject power loss at every persistent write boundary, including firmware, metadata, calibration, and post-install migration. |
| 8 | How should OTA signing keys be managed? | Private keys should be generated and used in an HSM or equivalent protected signing service with least privilege, multi-party approval for production signing, audit logs, rotation, backup, and revocation plans. Development and production trust domains remain separate. ECUs need a secure trust-anchor and certificate or key-update strategy that survives product lifetime. |
| 9 | What evidence supports SUMS and release traceability? | Evidence includes update identifiers, affected vehicle and ECU variants, source and artifact provenance, compatibility rules, test and approval records, SBOM, package hashes and signatures, signer identity, campaign authorization, installation status, failures, and rollback outcomes. Records must connect the approved software configuration to what was distributed and what each vehicle installed. |
| 10 | How would you test an OTA/SOTA workflow end to end? | I test authorized and unauthorized packages, corruption, replay, downgrade, wrong target, dependency mismatch, expired credentials, interrupted download, power loss, low storage, network loss, installation failure, rollback, and recovery. Backend, gateway, ECU, telemetry, and audit records are included. Tests run across supported variants and verify both cybersecurity controls and operational safety. |
