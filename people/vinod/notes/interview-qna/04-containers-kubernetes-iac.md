# Containers, Kubernetes, and Infrastructure as Code Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | Why use Docker for embedded builds when the output runs on an ECU? | Docker standardizes the host-side compiler, tools, libraries, and scripts even though the resulting binary targets an ECU. This reduces workstation drift and improves CI reproducibility. The image must still pin external inputs and cross-toolchains; a container alone does not guarantee reproducibility if it downloads mutable dependencies or relies on undeclared mounts. |
| 2 | What practices make a secure and maintainable build image? | I use a minimal trusted base, pin versions or digests, use multi-stage builds, run as non-root where possible, remove package caches, avoid embedded secrets, and scan the final image. Labels record provenance, while regular rebuilds absorb security fixes. Toolchains are verified by checksum and the Dockerfile is reviewed and versioned with the pipeline. |
| 3 | How would Kubernetes support Jenkins build workloads? | Jenkins can launch ephemeral agent pods from versioned templates, giving each job isolated resources and a clean environment. Requests, limits, node selectors, volumes, service accounts, and network policy must match workload needs. Persistent caches need careful keys and permissions. Autoscaling improves utilization, while logs and pod events support diagnosis of infrastructure failures. |
| 4 | What is Infrastructure as Code in the context of this resume? | It means representing build images, Jenkins pipelines, Kubernetes workloads, and policies as version-controlled Dockerfiles, Jenkinsfiles, Groovy libraries, and manifests. Changes follow review and automated validation, then produce traceable deployments. This makes environments repeatable and auditable while reducing undocumented manual configuration in CI controllers or clusters. |
| 5 | How do you manage secrets in containerized CI? | Secrets belong in a dedicated secrets manager or protected CI credential store, injected only into authorized jobs for the shortest necessary time. They must not appear in images, source, command lines, artifacts, or logs. I apply least privilege, rotation, access auditing, masked output, and separate credentials for build, signing, and deployment duties. |
| 6 | What causes a pod to remain Pending or become OOMKilled? | Pending commonly means unsatisfied resource requests, node selectors, affinity, taints, quotas, or unavailable volumes. OOMKilled means the container exceeded its memory limit, though memory leaks or excessive parallelism may be the cause. I inspect pod events, scheduling decisions, usage metrics, limits, and workload behavior before resizing or changing concurrency. |
| 7 | How would you apply Kyverno policies to CI workloads? | Kyverno can validate or mutate Kubernetes resources using policy-as-code. I would require approved image registries, digest pinning, non-root execution, resource limits, read-only filesystems where practical, and prohibited privilege settings. Policies are tested in audit mode before enforcement, versioned, assigned owners, and paired with a documented exception process for legitimate build-tool constraints. |
| 8 | How do you prevent container cache poisoning or stale outputs? | Cache keys must include relevant source, toolchain, dependency lock, configuration, and architecture inputs. Shared caches are read-only where possible and writes are restricted to trusted jobs. Checksums validate downloaded content. Periodic cache-free builds compare outputs, and untrusted pull-request jobs do not publish into caches later consumed by protected release pipelines. |
| 9 | What observability would you add to a containerized CI platform? | I collect controller, agent, pod, node, queue, CPU, memory, storage, network, and job-stage metrics, with centralized structured logs and correlation identifiers. Grafana dashboards show capacity and trends, while alerts focus on actionable symptoms such as queue growth, pod launch failure, repository latency, or error-rate changes rather than every transient event. |
| 10 | How do you roll out an IaC change without disrupting releases? | I validate syntax and policy, test in an isolated environment, inspect the proposed diff, and use a staged rollout with health checks. Existing release jobs remain pinned during critical milestones. A reviewed rollback revision and compatibility plan are prepared before deployment. Post-change metrics and representative builds confirm both infrastructure health and artifact equivalence. |
