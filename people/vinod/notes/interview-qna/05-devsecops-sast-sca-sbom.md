# DevSecOps, SAST, SCA, and SBOM Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | How do SAST, DAST, and SCA differ? | SAST examines source or compiled code for weakness patterns without executing the system. DAST probes a running system through exposed interfaces. SCA identifies third-party components, licenses, and known vulnerabilities. Embedded pipelines often emphasize SAST and SCA early, while DAST applies to reachable services or test targets. None replaces threat analysis or expert review. |
| 2 | Where should security checks run in an embedded CI/CD pipeline? | Fast checks such as secrets detection, manifest validation, and incremental SAST should run on pull requests. Full SAST, SCA, container scans, and SBOM generation run on integration builds. Release candidates receive complete policy evaluation, integrity checks, signing, and evidence archival. Feedback should arrive early, while the release gate uses the exact promoted artifacts. |
| 3 | How do you define a useful vulnerability quality gate? | The gate combines severity with exploitability, component reachability, product context, fix availability, and policy deadlines. A simple CVSS cutoff produces noise and can block on irrelevant findings. Every exception should have an owner, rationale, compensating control, expiry date, and approval. New critical exposure in a reachable release component should normally stop promotion. |
| 4 | What is an SBOM, and why does an automotive product need one? | An SBOM is a machine-readable inventory of software components and relationships, commonly represented as SPDX or CycloneDX. It supports license compliance, supply-chain transparency, and rapid impact analysis when a CVE appears. It must identify versions and preferably hashes, be generated from resolved build inputs, and remain linked to the exact released product variant. |
| 5 | What are the differences between SPDX and CycloneDX? | Both are standard SBOM formats. SPDX has strong origins in license and package information and supports rich provenance, while CycloneDX is security-oriented and integrates components, services, dependencies, vulnerabilities, and attestations. Tool compatibility and customer requirements guide selection. Content accuracy, dependency relationships, version identity, and linkage to the artifact matter more than choosing a fashionable format. |
| 6 | How do you triage a CVE found in an embedded dependency? | I verify component identity and version, affected configuration, vulnerable code presence, reachability, required privileges, and exposure in each product variant. Then I assess severity in vehicle context, available patches, compatibility risk, and compensating controls. The decision, owner, target date, validation evidence, and affected releases are documented and tracked through closure. |
| 7 | How should false positives from static analysis be handled? | Findings should be reviewed against code flow and tool rules, then fixed, suppressed with precise justification, or escalated. Broad suppression files and permanent baselines hide new defects. I keep suppressions local, owned, reviewed, and periodically expired. The pipeline distinguishes accepted findings from unreviewed findings while preserving history for audits and rule tuning. |
| 8 | How do you secure the software supply chain in CI? | I protect source branches, require reviewed changes, isolate untrusted jobs, pin and verify dependencies, use approved registries, scan build images, restrict credentials, and produce immutable artifacts with provenance and signatures. Release jobs run on trusted agents with separation of duties. Logs, manifests, SBOMs, checksums, and attestations connect the source baseline to the delivered package. |
| 9 | What is the role of secrets scanning if secrets are stored in a vault? | A vault controls legitimate secret access, while scanning catches accidental credentials in source, history, images, logs, and configuration. Both are needed. A detected secret is treated as exposed: revoke or rotate it, assess usage, remove it from active content, and investigate history. Merely deleting the latest commit does not invalidate copied credentials. |
| 10 | How do you keep security tools from overwhelming developers? | I tune rules to the language and risk, suppress proven false positives narrowly, deduplicate findings, assign clear ownership, and show remediation guidance close to the change. New-code policies prevent legacy debt from blocking all work, while critical existing issues retain deadlines. Dashboards should emphasize exploitable risk and aging rather than maximizing raw finding counts. |
| 11 | What is Trivy, and where would you use it in CI/CD? | Trivy is a security scanner commonly used for container images, filesystems, repositories, Kubernetes resources, and Infrastructure as Code. It can detect known vulnerabilities, misconfigurations, exposed secrets, and license issues, and can generate SBOMs. I run fast repository and IaC scans on pull requests, scan the final immutable image or artifact during integration, and archive the report and SBOM with the release evidence. |
| 12 | What is Snyk, and what does it scan? | Snyk is a developer-focused security platform that scans open-source dependencies, source code, container images, and Infrastructure as Code. It integrates with source repositories, IDEs, and CI systems to identify issues and provide remediation guidance. I use it early in development for actionable feedback, then apply centrally managed policy and reporting in protected CI and release workflows. |
| 13 | How do Trivy and Snyk differ, and would you use both? | Trivy is well suited to lightweight command-line and CI scanning across images, filesystems, IaC, Kubernetes, secrets, vulnerabilities, and SBOMs. Snyk provides a broader managed platform with developer workflows, dependency intelligence, source analysis, governance, and issue tracking. Their capabilities overlap, so I select tools based on coverage, ecosystem, policy, deployment constraints, and cost. If both are used, I define ownership and deduplicate findings rather than creating duplicate gates. |
| 14 | How would you integrate Trivy into a container build pipeline? | I scan the Dockerfile and IaC before the build, build the image, then scan the exact image digest that may be promoted. The scan uses a controlled vulnerability database update, emits machine-readable results and an SBOM, and fails only according to approved severity and exception policy. I archive the tool version, database metadata, image digest, report, and SBOM so the result is reproducible and traceable. |
| 15 | How would you integrate Snyk into a Jenkins pipeline? | I use a protected Snyk service token from the Jenkins credential store, never from source or command arguments. Pull requests run targeted tests for changed code, dependencies, containers, or IaC, while protected branches publish monitored project snapshots for ongoing vulnerability alerts. Organization policy controls thresholds and ignores; reports are retained, and temporary exceptions require an owner, justification, and expiry date. |
| 16 | How do Trivy or Snyk help when scanning an embedded Linux product? | I scan dependency manifests, lockfiles, build containers, and the assembled root filesystem, not only the application repository. For Yocto or Buildroot outputs, package metadata and an SBOM improve component and version identification because target filesystems may lack a normal package database. Findings still require validation against the built variant, configuration, architecture, backported vendor patches, reachability, and actual deployment exposure. |
