# ASPICE SWE.5 Integration Process Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | What is the purpose of Automotive SPICE SWE.5? | SWE.5 ensures software units and components are integrated into larger software items in a planned sequence and that their interactions are verified against the software architecture and integration criteria. It expects an integration strategy, defined tests, bidirectional traceability, consistent results, defect handling, and evidence that the integrated software is ready for subsequent qualification testing. |
| 2 | What should a software integration strategy contain? | It should define integration scope, sequence, dependencies, environments, configurations, responsibilities, entry and exit criteria, regression approach, test selection, required tools, and handling of variants and stubs. The strategy should reflect architecture and risk. It must be maintainable as the product changes rather than being created only for an assessment. |
| 3 | How do SWE.4, SWE.5, and SWE.6 differ? | SWE.4 verifies individual software units against detailed design and unit requirements. SWE.5 integrates units into software components and verifies interfaces and architectural interaction. SWE.6 qualifies the completed software against software requirements. The levels have different objectives and traceability, although automation and test environments may be shared where their suitability is demonstrated. |
| 4 | What is bidirectional traceability, and why is it important? | Bidirectional traceability lets an assessor or engineer navigate from architecture or integration criteria to test cases and results, and from each test result back to its basis and configuration. It reveals missing coverage, unintended tests, and change impact. Links should be maintained in the engineering toolchain rather than reconstructed manually before an audit. |
| 5 | How do you select integration test cases? | I derive tests from software architecture, interfaces, dynamic behavior, error handling, resource constraints, and identified risks. Cases include normal paths, boundaries, invalid data, timing, startup and shutdown, communication loss, and component interaction. Coverage is reviewed against integration criteria, with regression selection based on affected interfaces and dependencies rather than only modified files. |
| 6 | What evidence would you show in an ASPICE assessment for SWE.5? | I would show the approved integration strategy, architecture and interface basis, test specifications, environment and configuration records, automated pipeline runs, results, coverage or completion status, anomaly records, traceability reports, reviews, release baselines, and evidence of corrective action. I would also demonstrate that daily practice matches the documented process. |
| 7 | How should failed integration tests be managed? | A failure is recorded with the exact baseline, environment, steps, observed and expected result, logs, severity, and owner. The team analyzes whether it is a product, test, requirement, environment, or configuration defect. Disposition and retest evidence remain traceable. Waivers require rationale, impact assessment, authorization, and a defined validity period. |
| 8 | How can CI/CD support ASPICE without becoming a compliance exercise? | CI can enforce baseline identity, execute repeatable integration sequences, collect test and quality evidence, maintain trace links, and prevent promotion when criteria fail. The process remains useful when gates reflect actual product risk and reports serve engineers first. Automation reduces manual evidence assembly, but reviews, anomaly decisions, and responsibility cannot be delegated to a tool. |
| 9 | How do you handle changes to an integration baseline? | Every change is reviewed for affected components, interfaces, variants, tests, cybersecurity controls, and release commitments. CI builds the new candidate from controlled inputs and executes the impacted regression scope. The baseline is promoted only after criteria pass and deviations are approved. Released baselines remain immutable; corrections create a new identifiable version. |
| 10 | What commonly causes an ASPICE integration process to receive weak findings? | Typical causes are a generic strategy disconnected from architecture, incomplete interface coverage, missing configuration identity, broken traceability, inconsistent anomaly handling, undocumented manual steps, and evidence assembled only before assessment. Another warning sign is a green dashboard that hides skipped or flaky tests. Sustainable practice and demonstrable outcomes matter more than document volume. |
