# Embedded Testing, HIL/SIL, and Debugging Interview Questions

| No. | Interview question | Detailed answer |
|---:|---|---|
| 1 | How do unit, integration, smoke, and regression tests differ? | Unit tests isolate small implementation elements. Integration tests verify interfaces and interactions among combined elements. Smoke tests quickly determine whether a build is stable enough for deeper testing. Regression tests check that existing behavior remains intact after change. A strong pipeline layers them by speed and diagnostic value, then adds target-dependent tests where needed. |
| 2 | When would you choose SIL instead of HIL? | I choose SIL for fast, repeatable, scalable testing of logic, interfaces, fault scenarios, and regressions before hardware is available. HIL is necessary for real I/O, timing, electrical behavior, bus interaction, target execution, and hardware fault injection. The most efficient strategy uses broad SIL coverage and focused HIL coverage tied to hardware-dependent risks. |
| 3 | How would you build a reliable automated smoke test? | The test starts from a controlled image and hardware state, flashes or deploys deterministically, confirms boot and basic health, exercises critical communication and core functions, and captures timestamps, versions, logs, and measurements. It has explicit timeouts and cleanup. A failure identifies the failed checkpoint, while infrastructure errors are distinguished from product failures. |
| 4 | Describe a systematic root-cause analysis approach. | I define the symptom precisely, preserve evidence, reproduce it, and compare with a known-good baseline. I narrow the responsible layer using logs, traces, debugger state, configuration diffs, change bisection, and controlled experiments. The root cause must explain all observations. I then verify the correction and add a regression test or detection control. |
| 5 | How do you debug a crash with Lauterbach? | I halt at the exception or inspect the retained crash state, then check program counter, stack pointer, fault registers, call stack, task context, memory map, and loaded symbols. I verify that the ELF matches the flashed binary. Watchpoints, trace, and conditional breakpoints help reproduce corruption while minimizing timing disturbance. |
| 6 | What is data-flow testing in embedded integration? | Data-flow testing follows inputs through producers, transformations, communication, consumers, and outputs, verifying values, timing, validity, freshness, and error handling at boundaries. It is useful in ADAS chains where a locally correct component can still consume stale or incorrectly scaled data. Instrumentation and synchronized traces expose where the flow diverges. |
| 7 | How do you test timing behavior? | I define deadlines, periods, jitter, latency paths, startup times, and worst-case conditions, then measure on representative hardware with synchronized timestamps or trace. Tests include CPU and bus load, competing tasks, cache effects, and error paths. Results are compared to budgets over enough samples; average latency alone cannot establish worst-case compliance. |
| 8 | How should flaky HIL tests be handled? | I measure frequency and correlate failures with hardware, wiring, power, environment, timing, test code, and product baselines. The setup needs health checks, calibration, deterministic reset, and captured diagnostics. Quarantine can protect the main signal temporarily, but it requires an owner and deadline. Blind retries hide risk and distort release evidence. |
| 9 | What value do VectorCAST and PRQA provide in CI? | VectorCAST supports automated unit and integration testing, coverage, and controlled test environments for C/C++. PRQA performs static code analysis and coding-standard checks. In CI, both provide repeatable evidence and early feedback. Their configurations and suppressions must be versioned, reviewed, and matched to project risk rather than treated as automatic proof of quality. |
| 10 | How do you distinguish a software defect from a test-infrastructure defect? | I compare independent observations, rerun on known-good software, move the same build to another bench, inspect bench health and setup logs, and reproduce with a simpler stimulus. A product defect follows the software or input condition; an infrastructure defect follows the bench or harness. The classification remains evidence-based and both types receive tracked corrective action. |
